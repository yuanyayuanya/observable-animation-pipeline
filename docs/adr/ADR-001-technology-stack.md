# ADR-001：MVP 技术栈

- 状态：已接受
- 日期：2026-10-07
- 决策范围：题目 D 单机可观测任务管线 MVP

## 背景

项目需要在有限时间和磁盘空间内展示持久任务、失败恢复、可观测性和结果复用。电脑已有 Python、Uvicorn、SQLAlchemy、pytest、OpenCV 和 Pillow；项目不需要真实 AI 模型或 GPU 推理。

## 决策

| 领域 | 选择 |
|---|---|
| Web API | FastAPI + Uvicorn |
| 数据访问 | SQLAlchemy 2.x |
| 数据库 | SQLite + WAL |
| Worker | 独立 Python 进程，数据库轮询与租约领取 |
| 视频处理 | OpenCV |
| 图片处理 | Pillow |
| 前端 | 服务端静态 HTML、CSS、原生 JavaScript |
| 状态刷新 | 每秒 HTTP 轮询，事件增量读取 |
| 测试 | pytest |
| 文件存储 | E 盘本地 Artifact Store |

## 理由

### FastAPI

接口类型清晰，自动生成 OpenAPI，适合快速实现可检查的任务 API。电脑仅缺少这一项依赖，新增磁盘占用很小。

### SQLite WAL

题目允许单机 MVP。SQLite 能持久保存任务状态并提供事务，WAL 允许 API 读取和 Worker 写入并存。它不适合跨机器高写入，但足以验证租约、状态机和恢复语义。

### 数据库轮询 Worker

避免引入 Redis、RabbitMQ 和 Celery，把重点放在题目关心的状态与恢复设计上。Worker 使用条件更新领取步骤，协议可以被自动测试。

### 原生前端

页面只有任务列表、任务详情和操作按钮，不需要前端构建链。这样减少 `node_modules`、磁盘占用和环境故障，同时仍可实现完整交互。

### HTTP 轮询

每秒轮询对单用户演示足够稳定，刷新页面也容易恢复。SSE 或 WebSocket 可以降低请求数，但会增加连接重连和状态同步测试范围。

## 放弃的方案

### Celery + Redis

优点是成熟的任务分发与重试；缺点是引入额外服务，且容易把核心恢复行为交给框架，评审者难以看清本项目的设计。

### Temporal

工作流语义完整，但安装和运行成本更高，对本次单机 MVP 过重。README 会说明生产系统何时应选择 Temporal，而不是假装自研调度器适合所有场景。

### React/Vite

能提升组件开发体验，但会带来额外依赖和磁盘占用。原生页面足以完成工作型界面。

### Docker

便于环境复现，但当前 C 盘空间紧张，Docker Desktop 和镜像成本不合理。项目先提供明确的 Python 启动命令。

## 后果

正面影响：

- 依赖少，适合当前电脑。
- 状态与恢复逻辑完全可检查和测试。
- API、Worker 和数据文件可以独立重启。
- 项目空间可控制在 2-3 GB 峰值以内。

限制：

- SQLite 不适合多机 Worker。
- 本地文件存储不具备跨节点共享能力。
- 每秒轮询不适合大量同时在线用户。
- 自研租约协议只服务于本题，不替代成熟工作流引擎。

## 未来迁移

当出现多机器、数百并发任务或跨区域执行需求时：

1. SQLite 迁移到 PostgreSQL。
2. 本地 Artifact Store 迁移到 S3 兼容对象存储。
3. Worker 领取和恢复迁移到 Temporal 或成熟队列系统。
4. 页面状态更新迁移到 SSE。
5. GPU 资源租约迁移到具备显存和优先级感知的调度器。
